Critical purchase flows
- The server validates contacts, delivery/payment options, product IDs, prices,
  quantities and totals before inserting an order.
- Initial order/payment statuses come from the server.
- An uncertain response preserves the request ID for a retry in the same tab.
- The real client helper and API are tested together after a lost response and
  simulated client-module reload. There is one saved row and one notification.
- Simultaneous identical client calls now share an in-flight promise.
  This fixes a race found by the new integration test.
- Concurrent API requests are tested separately against a simulated unique key.
- Concurrent inserts were also verified against isolated local PostgreSQL.
- Telegram failures do not turn a saved order into a failed purchase.
- Cart cleanup subtracts submitted quantities from the latest cart state.
  Later additions and selection changes survive; verified in the browser and
  after a page reload using a delayed synthetic local API.
