1. WHY DID YOU CHOOSE REACT INSTEAD OF VANILLA JAVASCRIPT?
Чому ти обрала React замість звичайного JavaScript?

Answer in English:
I chose React because my shop has reusable components and interactive features.
For example, I can reuse a product card for many products.
React helps me manage the cart, filters and forms through state.
I describe what the interface should show, and React updates it when state changes.
For a small static website, plain HTML, CSS and JavaScript could be simpler
and would not require the extra React library.

Повний переклад українською:
Я обрала React, тому що мій магазин має компоненти, які можна використовувати
повторно, та інтерактивні функції.
Наприклад, я можу використовувати одну картку товару для багатьох товарів.
React допомагає мені керувати кошиком, фільтрами та формами через стан.
Я описую, що має показувати інтерфейс, і React оновлює його, коли стан змінюється.
Для невеликого статичного сайту звичайні HTML, CSS і JavaScript могли б бути
простішим рішенням і не потребували б додаткової бібліотеки React.

Що реалізовано і для чого:
Магазин поділено на компоненти, зокрема Header, Footer, ProductCard і CartDrawer.
ProductCard отримує дані товару через props, тому розмітку картки не потрібно
писати заново для кожного товару. Стан визначає, які товари видно і що є в кошику.
Такий поділ допомагає знаходити потрібний код і змінювати окрему частину сайту.
Приклад у коді: src/components/ProductCard/ProductCard.tsx.


2. WHY DID YOU CHOOSE CSS MODULES, AND WHAT ARE THE TRADE-OFFS COMPARED WITH TAILWIND?
Чому ти обрала CSS Modules і які переваги та недоліки бачиш порівняно з Tailwind?

Answer in English:
I prefer CSS Modules because separate style files are easier for me to read and edit.
Personally, I find long lists of Tailwind utility classes in JSX harder to read.
With CSS Modules, my markup stays shorter, and my styles are clearly organized.
I can quickly find the part I need to change.
CSS Modules also help prevent class name conflicts.
Tailwind can be useful for fast styling, but CSS Modules suit my workflow better.
The trade-off is that I write and maintain separate CSS files and class names.

Повний переклад українською:
Я віддаю перевагу CSS Modules, тому що окремі файли стилів мені легше читати
та редагувати.
Особисто мені складніше читати довгі списки допоміжних класів Tailwind у JSX.
З CSS Modules моя розмітка залишається коротшою, а стилі мають чітку структуру.
Я можу швидко знайти частину, яку потрібно змінити.
CSS Modules також допомагають уникати конфліктів назв класів.
Tailwind може бути корисним для швидкого оформлення, але CSS Modules краще
підходять до мого способу роботи.
Компроміс полягає в тому, що я пишу й підтримую окремі CSS-файли та назви класів.

Що реалізовано і для чого:
У проєкті збережено CSS Modules: стилі компонента розміщені в його .module.css.
Під час збірки локальні назви класів перетворюються, щоб однойменні класи
різних модулів не конфліктували. Спільні CSS-змінні допомагають підтримувати
однакове оформлення сайту; глобальні стилі також залишаються в проєкті.
Під час покращень ми зберегли цей підхід і візуальний стиль магазину.
Tailwind не використовуємо. Довгі списки класів — питання твоєї зручності читання,
а не твердження, що Tailwind обов'язково створює поганий код.
Приклад у коді: src/components/ProductCard/ProductCard.module.css.


3. HOW DID YOU DECIDE BETWEEN LOCAL STATE AND SHARED STATE?
Як ти вирішувала, де використовувати локальний стан, а де спільний?

Answer in English:
I use local state for form values and filters where they are needed.
I use React Context for the cart because several components need the same cart data.
For example, the cart drawer and checkout both use it.
The provider stores the cart state, and Context makes it available to other components.
I also save the cart in localStorage so it survives a page refresh.
Redux would add complexity that I do not need for the current project.

Повний переклад українською:
Я використовую локальний стан для значень форм і фільтрів там, де вони потрібні.
Я використовую React Context для кошика, тому що кільком компонентам потрібні
ті самі дані кошика.
Наприклад, їх використовують і панель кошика, і сторінка оформлення замовлення.
Провайдер зберігає стан кошика, а Context робить його доступним іншим компонентам.
Я також зберігаю кошик у localStorage, щоб він залишався після оновлення сторінки.
Redux додав би складності, яка мені не потрібна в поточному проєкті.

Що реалізовано і для чого:
CartProvider використовує useState для кошика та передає дані й функції через Context.
Це дозволяє різним частинам магазину працювати з одним актуальним кошиком.
Під час покращень ми також забезпечили збереження змін, зроблених під час
оформлення: після успішного замовлення віднімаються замовлені кількості,
а товари, додані пізніше, залишаються. Це захищає нові дії покупця від втрати.
Context передає стан; localStorage зберігає його між завантаженнями сторінки.
Приклад у коді: src/context/CartContext.tsx; src/pages/Checkout/Checkout.tsx.


4. HOW DOES YOUR INTERFACE HANDLE FAILED, SLOW OR EMPTY DATA REQUESTS?
Як інтерфейс обробляє невдалі, повільні запити або порожні результати?

Answer in English:
The catalogue loads data from a JSON file and has loading, success, error and empty states.
While the request is pending, the user sees a loading message.
If it fails, the interface shows an error instead of silently showing nothing.
If no products match the filters, it shows an empty result message.
A failed checkout keeps the cart so the customer can try again.
There is no custom catalogue request timeout yet, so a very slow request may keep loading.

Повний переклад українською:
Каталог завантажує дані з JSON-файлу й має стани завантаження, успіху, помилки
та порожнього результату.
Поки запит очікує завершення, користувач бачить повідомлення про завантаження.
Якщо запит не вдається, інтерфейс показує помилку, а не просто нічого не відображає.
Якщо жоден товар не відповідає фільтрам, він показує повідомлення про порожній результат.
Невдала спроба оформлення зберігає кошик, щоб покупець міг спробувати ще раз.
Власного обмеження часу запиту каталогу поки немає, тому дуже повільний запит
може залишатися у стані завантаження.

Що реалізовано і для чого:
У Home окремо зберігаються товари, стан завантаження та повідомлення про помилку.
Це дозволяє відрізняти очікування від збою та від відсутності результатів.
Замовлення надсилаються до серверного /api/orders; сервер записує їх у Supabase.
Повторна спроба тієї самої операції використовує той самий request_id,
а сервер перевіряє його, щоб не створювати дубль уже збереженого замовлення.
Кошик змінюється після підтвердженого успіху. Власний таймер скасування
запиту каталогу не реалізований — це можливе майбутнє покращення.
Приклад у коді: src/pages/Home.tsx; src/pages/Checkout/Checkout.tsx; api/orders.ts.


5. WHAT HAPPENS WHEN STATE CHANGES, AND WHY DO LIST ITEMS NEED KEYS?
Що відбувається, коли стан змінюється, і навіщо елементам списку потрібні ключі?

Answer in English:
When I change a filter, the component state changes.
React calculates the next interface, compares it with the previous one,
and updates the necessary parts of the DOM.
I use product.id as the key so React can identify each product across updates.
Using an array index can cause problems when items are reordered or removed.
Stable keys help React preserve the correct identity and state of list items.

Повний переклад українською:
Коли я змінюю фільтр, змінюється стан компонента.
React обчислює наступний вигляд інтерфейсу, порівнює його з попереднім
і оновлює необхідні частини DOM.
Я використовую product.id як ключ, щоб React міг розпізнавати кожен товар
між оновленнями.
Використання індексу масиву може спричинити проблеми, коли елементи змінюють
порядок або видаляються.
Стабільні ключі допомагають React зберігати правильну ідентичність і стан елементів списку.

Що реалізовано і для чого:
У списку карток використовується key={product.id}. Ключ має бути стабільним
і унікальним серед сусідніх елементів; випадкові значення для цього не підходять.
Окремо у ProductResults ключ навмисно залежить від пошуку та фільтрів.
Його зміна створює компонент заново й скидає показ до перших 24 товарів,
щоб новий пошук не успадковував кількість карток від попереднього.
Це інше призначення ключа, ніж збереження ідентичності окремої картки товару.
Приклад у коді: src/pages/Home.tsx.


6. HOW DO YOU OPTIMIZE THE PRODUCTION BUILD AND PERFORMANCE?
Як ти оптимізуєш виробничу збірку та продуктивність?

Answer in English:
Vite bundles and minifies the production code and can remove unused code.
My routes use lazy loading, so page code can load when it is needed.
During the improvements, we converted large background images to WebP
and changed the catalogue to show products in batches of 24.
This reduces image download size and the number of cards rendered at once.
The catalogue still downloads as one large JSON file, so this can be improved later.

Повний переклад українською:
Vite збирає та мінімізує виробничий код і може видаляти невикористаний код.
Мої маршрути використовують відкладене завантаження, тому код сторінки
може завантажуватися тоді, коли він потрібен.
Під час покращень ми перетворили великі фонові зображення у WebP
і змінили каталог, щоб він показував товари порціями по 24.
Це зменшує обсяг завантаження зображень і кількість карток, які відображаються одночасно.
Каталог усе ще завантажується одним великим JSON-файлом, тому це можна покращити пізніше.

Що реалізовано і для чого:
Сторінки підключаються через React.lazy та Suspense. Для зображень товарів
використовується відкладене завантаження, а великі фони оптимізовано без зміни пікселів.
Кнопка показу наступних товарів додає ще 24 картки: браузер не створює одразу
тисячі елементів. Це обмеження відображення, а не серверна пагінація.
Команда build спочатку перевіряє TypeScript, потім виконує виробничу збірку.
Автоматичне видалення всіх console.log не налаштоване; очищення Tailwind CSS
не застосовується, оскільки Tailwind у проєкті немає.
Приклад у коді: src/App.tsx; src/pages/Home.tsx; package.json.


7. WHY USE A NATIVE BUTTON INSTEAD OF A CLICKABLE DIV?
Чому варто використовувати звичайну HTML-кнопку замість div з обробником кліку?

Answer in English:
A native button already supports keyboard focus and activation.
Users can reach it with Tab and activate it with Enter or Space.
Screen readers recognize its button role.
A clickable div needs extra keyboard handling and accessibility information.
I also give icon buttons accessible names and keep focus visible.
This makes the controls easier to use without a mouse.

Повний переклад українською:
Звичайна HTML-кнопка вже підтримує фокус і активацію з клавіатури.
Користувачі можуть перейти до неї клавішею Tab та активувати через Enter або пробіл.
Програми читання з екрана розпізнають її роль кнопки.
Div з обробником кліку потребує додаткової обробки клавіатури та інформації
для допоміжних технологій.
Я також додаю доступні назви кнопкам з іконками та зберігаю видимий фокус.
Це робить елементи керування зручнішими для використання без миші.

Що реалізовано і для чого:
Під час покращень додано доступні назви й стани інтерактивних елементів,
видимі індикатори фокуса та покращення клавіатурної роботи з інтерфейсом.
Для дій використовуються button, для переходів — посилання.
Кнопкам у формі, які не надсилають її, потрібен type="button",
щоб випадково не запустити оформлення замовлення.
Ці зміни допомагають користувачам клавіатури й допоміжних технологій.
Повного аудиту контрасту та перевірки зі скринрідером ще не виконано.
Приклад у коді: src/components/Header/Header.tsx; src/pages/Checkout/Checkout.tsx.


8. HOW DID YOU PRIORITIZE YOUR WORK, AND WHAT DID YOU POSTPONE?
Як ти визначала пріоритети роботи та що відклала?

Answer in English:
The shop existed before this assessment preparation.
I focused on the main customer journey: finding a product, using the cart
and placing an order.
During the improvements, I prioritized security, error handling, accessibility and testing.
I postponed German localization, more brands and online payment integration.
These features are important for future business development, but they are outside the current scope.

Повний переклад українською:
Магазин існував ще до цієї підготовки до оцінювання.
Я зосередилася на основному шляху покупця: пошуку товару, використанні кошика
та оформленні замовлення.
Під час покращень я надала пріоритет безпеці, обробці помилок, доступності та тестуванню.
Я відклала німецьку локалізацію, додавання інших брендів та інтеграцію онлайн-оплати.
Ці можливості важливі для майбутнього розвитку бізнесу, але вони виходять
за межі поточного обсягу робіт.

Що реалізовано і для чого:
Покращення виконувалися поступово зі збереженням наявного дизайну й архітектури.
Зокрема, ми перенесли запис замовлень на сервер і підготували обмеження доступу
до таблиці orders; ти застосувала SQL та підтвердила права доступу в Supabase.
Для anon і authenticated закрито пряме читання та зміну замовлень,
а приватний серверний ключ використовується на сервері.
У підсумковому звіті записано 73 успішні автоматизовані тести, перевірки lint,
TypeScript і виробничої збірки. Це попередні результати, а не новий запуск тут.
Авторизація через Clerk уже існує; її не слід називати відкладеною функцією.
Банківський переказ не означає автоматичне списання коштів або підтвердження оплати.
Приклад у коді: api/orders.ts; scripts/secure-order-access.sql.


9. DESCRIBE ONE REAL BUG AND YOUR STEP-BY-STEP DEBUGGING PROCESS
Опиши одну реальну помилку та послідовність її діагностики.

Answer in English:
Checkout failed on the old GitHub Pages address, but it worked on the main site.
First, I compared the results on the two addresses.
I confirmed that an order from the main site appeared in Supabase
and that the Telegram notification arrived.
With AI assistance, I identified the difference between the hosting setups:
GitHub Pages cannot run our server-side order API, while Vercel can.
We redirected the old address to the main site, and I checked that it worked.

Повний переклад українською:
Оформлення замовлення не працювало за старою адресою GitHub Pages,
але працювало на основному сайті.
Спочатку я порівняла результати за двома адресами.
Я підтвердила, що замовлення з основного сайту з'явилося в Supabase
та що повідомлення в Telegram надійшло.
За допомогою AI я визначила різницю між налаштуваннями хостингу:
GitHub Pages не може виконувати наш серверний API замовлень, а Vercel може.
Ми перенаправили стару адресу на основний сайт, і я перевірила, що це працює.

Що реалізовано і для чого:
Стара GitHub Pages-версія тепер слугує перенаправленням на основний сайт.
Основний сайт на Vercel обслуговує інтерфейс і /api/orders, який записує
замовлення в Supabase та надсилає повідомлення Telegram.
Це прибирає ситуацію, коли покупець бачить магазин, але не може оформити замовлення
через відсутній на старому хостингу серверний обробник.
Ти самостійно виконувала коміти, публікацію та перевірку результату.
Тоді у Vercel Logs не було видно потрібного запиту — не потрібно вигадувати,
що причина була знайдена через конкретний POST-запис у логах.
Приклад у коді: scripts/build-github-redirect.js; api/orders.ts.


10. HOW WOULD YOU SUPPORT 50,000 DAILY USERS AND MULTIPLE LANGUAGES?
Як би ти підготувала застосунок до 50 000 користувачів на день і кількох мов?

Answer in English:
First, I would measure traffic and find the main bottlenecks.
I would replace the large catalogue download with paginated API requests.
I would consider caching and add monitoring and protection against too many requests.
For multiple languages, I would move interface text into translation files.
The project already uses lazy loading and shared CSS variables.
The other changes are future plans; the current version has not been tested for that traffic.

Повний переклад українською:
Спочатку я виміряла б трафік і знайшла основні місця, які обмежують продуктивність.
Я замінила б завантаження великого каталогу запитами до API з пагінацією.
Я розглянула б кешування та додала моніторинг і захист від надмірної кількості запитів.
Для кількох мов я перенесла б тексти інтерфейсу у файли перекладів.
У проєкті вже використовуються відкладене завантаження та спільні CSS-змінні.
Інші зміни — це плани на майбутнє; поточну версію не тестували на такий трафік.

Що реалізовано і для чого:
Наразі сторінки завантажуються за потреби, частина зображень — відкладено,
а картки показуються порціями. Це зменшує початкову роботу браузера.
Повноцінного API каталогу з пагінацією, багатомовності та перевіреного
масштабування на зазначену аудиторію ще немає. React Query також не використовується.
Майбутня серверна пагінація дозволила б отримувати лише потрібну частину каталогу,
а переклади в окремих файлах — змінювати мову без дублювання компонентів.
50 000 користувачів за день не дорівнюють 50 000 одночасних користувачів:
для планування потрібно знати пікове навантаження та результати вимірювань.

11. CAN YOU EXPLAIN WHAT HAPPENS WHEN A CUSTOMER PLACES AN ORDER?

12. WHY DO YOU VALIDATE ON BOTH THE CLIENT AND THE SERVER? CAN A CUSTOMER CHANGE THE PRICE?
Навіщо перевірки і на клієнті, і на сервері? Чи може покупець підмінити ціну?

Answer in English:
Client validation gives quick feedback, but a user can bypass it.
The server must check the request independently.
It looks up product IDs, availability and prices in its catalogue and calculates the total.
If the submitted price or total is different, it rejects the order.
I calculate money in integer kopiykas to reduce floating-point errors.

Повний переклад українською:
Перевірка на клієнті дає швидкий зворотний зв'язок, але користувач може її обійти.
Сервер повинен перевіряти запит незалежно.
Він знаходить ідентифікатори товарів, наявність і ціни у своєму каталозі та обчислює суму.
Якщо надіслана ціна або сума відрізняються, він відхиляє замовлення.
Я обчислюю гроші в цілих копійках, щоб зменшити похибки чисел із рухомою комою.

Що реалізовано і для чого:
У Checkout перевіряються поля для зручності покупця; в API ті самі дані
перевіряються повторно, бо запит можна надіслати без інтерфейсу магазину.
buildOrderFromCatalogue бере інформацію із серверного products.json і не довіряє
назві, статусу або сумі, переданим браузером. Кількість має бути додатним цілим числом.
Наприклад, 12,50 грн обчислюються як 1250 копійок. Сервер сам задає статус new.
Можливе уточнення: «Does required make the API secure?» — ні, це лише браузерна перевірка.

13. WHAT PREVENTS DUPLICATE ORDERS IF THE USER CLICKS TWICE OR LOSES THE RESPONSE?
Що запобігає дублям при подвійному натисканні або втраті відповіді сервера?

Answer in English:
The form blocks repeated submission while a request is pending.
For the same unresolved purchase, the client reuses a request UUID stored in sessionStorage.
The server uses that UUID as the order ID and checks for an existing order.
A matching retry returns the existing receipt instead of saving another order.
This continuity depends on the same data and browser tab.

Повний переклад українською:
Форма блокує повторне надсилання, поки запит очікує завершення.
Для тієї самої покупки без підтвердженого результату клієнт повторно використовує
UUID запиту, збережений у sessionStorage.
Сервер використовує цей UUID як ідентифікатор замовлення та перевіряє наявний запис.
Повторний запит із тими самими даними повертає наявне підтвердження замість нового запису.
Збереження цієї послідовності залежить від тих самих даних і вкладки браузера.

Що реалізовано і для чого:
Сервер міг зберегти замовлення, навіть якщо браузер не отримав відповідь.
Тому повторна спроба використовує той самий request_id. Унікальний первинний ключ
у базі також захищає від одночасного запису двох замовлень з одним ID.
Це приклад ідемпотентності: повторення тієї самої операції не створює нової покупки.
Для ID з іншими даними сервер повертає 409. Після підтвердженого успіху маркер
видаляється, щоб наступна свідома покупка могла мати новий ID.
Можливе уточнення: «What if the tab is closed?» — маркер може втратитися;
це не гарантія захисту від усіх можливих дублів між вкладками та пристроями.
Приклад у коді: src/lib/submitOrder.ts; api/orders.ts; tests/checkout-flow.test.mjs.


14. WHAT HAPPENS IF TELEGRAM IS UNAVAILABLE AFTER THE ORDER IS SAVED?
Що станеться, якщо Telegram недоступний після збереження замовлення?

Answer in English:
Supabase stores the order before the server attempts the notification.
A Telegram failure does not delete the order or turn it into a failed database save.
The customer can still receive a successful order receipt.
There is no automatic notification retry queue yet.
The owner can check orders in Supabase if a notification is missing.

Повний переклад українською:
Supabase зберігає замовлення до спроби сервера надіслати повідомлення.
Збій Telegram не видаляє замовлення й не перетворює його на невдале збереження в базі.
Покупець усе одно може отримати успішне підтвердження замовлення.
Автоматичної черги повторного надсилання повідомлень поки немає.
Власниця може перевірити замовлення в Supabase, якщо повідомлення відсутнє.

Що реалізовано і для чого:
Повідомлення — додаткова дія після основної операції збереження.
Окрема обробка помилки не змушує покупця створювати повторне замовлення через збій бота.
Важлива точність: виклик Telegram усе ще очікується через await, окремого тайм-ауту
немає. Дуже повільний Telegram може затримати відповідь API. Не кажи, що повідомлення
вже надсилаються незалежною фоновою чергою або гарантовано доставляються.
Приклад у коді: api/orders.ts, sendTelegramOrderNotification і вкладений try/catch.

16. WHAT DO THE FRONTEND, VERCEL API AND DATABASE EACH DO? WHY POST?
Що окремо роблять фронтенд, API на Vercel і база даних? Чому використовується POST?

Answer in English:
The frontend runs in the browser and handles the interface.
A Vercel serverless function handles the order request on the server.
Supabase stores the resulting order in PostgreSQL.
The browser sends JSON with POST because it is submitting a new order.
The API returns an HTTP status and a JSON receipt or error.

Повний переклад українською:
Фронтенд працює в браузері й відповідає за інтерфейс.
Серверна функція Vercel обробляє запит замовлення на сервері.
Supabase зберігає отримане замовлення в PostgreSQL.
Браузер надсилає JSON через POST, тому що передає нове замовлення.
API повертає HTTP-статус і підтвердження або помилку у форматі JSON.

Що реалізовано і для чого:
Serverless означає, що хостинг запускає серверну функцію за запитом;
це не означає відсутність серверного коду. Браузер не виконує api/orders.ts.
POST /api/orders приймає заявку. GET цього endpoint повертає 405 — метод не підтримується.
201 означає новий збережений запис; 200 — підтверджений повторний запит;
400 — некоректні поля; 409 — конфлікт ціни, суми або даних; 500 — помилку обробки.
Для fetch потрібно перевіряти response.ok: статус 400 сам собою не є мережевим винятком.
Приклад у коді: src/lib/submitOrder.ts; api/orders.ts; vercel.json.


17. HOW DO YOU PROTECT SECRET KEYS AND CUSTOMER ORDERS?

Private Supabase and Telegram credentials stay on the server.

The public order endpoint still needs future protection against spam and excessive requests.

22. HOW DO PROPS AND STATE DIFFER, AND WHY USE FUNCTIONAL STATE UPDATES?
Чим props відрізняються від state і навіщо функціональне оновлення стану?

Answer in English:
Props pass data into a component, while state stores data that can change.
ProductCard receives a product through props and keeps its dialog state locally.
Cart updates use the previous state to calculate the next state.
I create new arrays and objects instead of changing the existing state directly.
This makes updates predictable and avoids using an outdated cart value.

Повний переклад українською:

23. WHAT IS useEffect USED FOR? WHY DO DEPENDENCIES AND CLEANUP MATTER?

I use effects to synchronize React with things outside rendering.

Dependencies tell React when an effect needs to run again.
Cleanup removes event listeners or prevents an old request from updating an inactive component.

24. WHY USE useMemo AND useRef? HOW ARE THEY DIFFERENT FROM useState?
Навіщо useMemo та useRef? Чим вони відрізняються від useState?

Answer in English:
useState stores values that affect the interface and schedules a render when updated.
useMemo can reuse a calculated value while its dependencies stay the same.
I use it for filtered product lists.
useRef keeps a value between renders without triggering a render when it changes.
In checkout, a ref guards submission, while state controls the visible submitting status.

Повний переклад українською:
useState зберігає значення, які впливають на інтерфейс, і планує рендер при оновленні.
useMemo може повторно використовувати обчислене значення, поки його залежності не змінюються.
Я використовую його для відфільтрованих списків товарів.
useRef зберігає значення між рендерами й не запускає рендер при його зміні.
В оформленні ref захищає від повторного надсилання, а state керує видимим станом надсилання.

Що реалізовано і для чого:
useMemo не є глобальним кешем і не робить API-запит. Він допомагає уникати
повторних обчислень у компоненті. Програма має бути правильною і без цієї оптимізації.
submissionInProgress.current можна перевірити й змінити одразу, а isSubmitting
потрібен для оновлення кнопки та інтерфейсу. Ref також може посилатися на DOM:
dialogRef у useModalFocus знаходить елементи діалогу для роботи з фокусом.
Можливе уточнення: «What about useCallback?» — він може зберігати посилання
на функцію між рендерами. У ProductCard так стабілізується closeDetails;
useMemo зберігає результат обчислення, а useCallback — саму функцію.

31. WHAT DOES useState RETURN, AND WHY NOT USE A NORMAL VARIABLE?
Що повертає useState і чому не використати звичайну змінну?

Answer in English:
useState returns the current state value and a setter function.
For example, isMenuOpen describes whether the mobile menu is open,
and setIsMenuOpen requests an update.
React keeps state between renders.
Changing a normal local variable does not tell React to update the interface.
The initial value is used when that component instance first initializes.

Повний переклад українською:
useState повертає поточне значення стану та функцію для його оновлення.
Наприклад, isMenuOpen описує, чи відкрите мобільне меню,
а setIsMenuOpen запитує оновлення.
React зберігає стан між рендерами.
Зміна звичайної локальної змінної не повідомляє React, що потрібно оновити інтерфейс.
Початкове значення використовується при першій ініціалізації цього екземпляра компонента.

Що реалізовано і для чого:
const [isMenuOpen, setIsMenuOpen] = useState(false);
Квадратні дужки тут — деструктуризація масиву з двох значень.
false означає, що меню спочатку закрите. setIsMenuOpen(true) задає наступний стан.
Компонент виконується знову, а React зіставляє результат із попереднім інтерфейсом.
Якщо наступне значення дорівнює попередньому за Object.is, React може пропустити оновлення.
У CartProvider використано useState(() => ...): функція ліниво обчислює
початковий кошик із localStorage, а не перечитує його при кожному рендері.
Можливе уточнення: «Does the setter return the new state?» — ні, використовуємо
значення стану під час наступного рендера.
Приклад у коді: src/components/Header/Header.tsx; src/context/CartContext.tsx.


32. DOES STATE CHANGE IMMEDIATELY AFTER THE SETTER? WHEN DO YOU USE THE PREVIOUS VALUE?
Чи змінюється state одразу після setter? Коли використовують попереднє значення?

Answer in English:
The setter queues an update for a later render.
The current event handler still sees the state snapshot from its render.
If the next value depends on the previous one, I use a functional update.
For example, the load-more button calculates the next count from the previous count.
React can group several updates together.

Повний переклад українською:
Setter ставить оновлення в чергу для наступного рендера.
Поточний обробник події все ще бачить знімок стану зі свого рендера.
Якщо наступне значення залежить від попереднього, я використовую функціональне оновлення.
Наприклад, кнопка показу наступних товарів обчислює нову кількість із попередньої.
React може об'єднувати кілька оновлень.

Що реалізовано і для чого:
У ProductResults використовується setVisibleCount(count => Math.min(count + 24, products.length)).
count у цій функції — актуальний стан із черги оновлень. Той самий підхід
використовується в setCartItems(prevItems => ...).
Навчальний приклад, не фрагмент магазину: якщо count = 0, два виклики
setCount(count + 1) в одному обробнику зазвичай задають 1 і 1, а не послідовні 1 і 2.
Два виклики setCount(c => c + 1) послідовно обчислять 1 і 2.
Не пояснюй setter як Promise, який можна просто await для отримання нового стану.

33. WHAT IS A CONTROLLED INPUT, AND HOW DOES onChange WORK IN YOUR FORM?
Що таке контрольоване поле та як onChange працює у твоїй формі?

Answer in English:
A controlled input receives its value from React state.
When the user types, onChange reads the input value and updates that state.
The next render displays the updated value.
In checkout, formData stores the fields together.
When I update one field, I copy the other fields so they are preserved.

Повний переклад українською:
Контрольоване поле отримує своє значення зі стану React.
Коли користувач вводить текст, onChange читає значення поля та оновлює цей стан.
Наступний рендер показує оновлене значення.
У формі оформлення formData зберігає поля разом.
Коли я оновлюю одне поле, я копіюю інші, щоб зберегти їх.

Що реалізовано і для чого:
value={formData.name}
onChange={(e) => setFormData({...formData, name: e.target.value})}
value визначає показаний текст. e.target.value — новий текст із поля.
Spread ...formData зберігає email, phone та інші поля, а name замінюється.
Setter useState не зливає об'єкти автоматично: переданий об'єкт стає новим значенням.
Якщо залишити value, але не оновлювати стан в onChange, поле не працюватиме
як звичайне редаговане поле. Для неконтрольованого поля браузер зберігає
поточне значення сам; defaultValue задає лише початкове значення.
Приклад у коді: src/pages/Checkout/Checkout.tsx; пошукове поле в Header.tsx.


34. HOW DO YOU HANDLE A CLICK? WHY PASS A FUNCTION INSTEAD OF CALLING IT IN JSX?
Як ти обробляєш клік? Чому в JSX передають функцію, а не викликають її одразу?

Answer in English:
I pass an event handler to onClick so React can call it when the user clicks.
onClick={openDetails} passes a function.
onClick={openDetails()} would call it during rendering.
If I need to pass a product, I use a wrapper such as an arrow function.
The event object gives information about the interaction.

Повний переклад українською:
Я передаю обробник події в onClick, щоб React міг викликати його після кліку користувача.
onClick={openDetails} передає функцію.
onClick={openDetails()} викликав би її під час рендера.
Якщо потрібно передати товар, я використовую обгортку, наприклад стрілкову функцію.
Об'єкт події надає інформацію про взаємодію.

Що реалізовано і для чого:
Кнопка зображення товару використовує onClick={openDetails}.
onClick={() => addToCart(product)} викликає додавання саме потрібного товару
після кліку. Arrow function тут потрібна для передавання аргументу, а не для
автоматичного покращення продуктивності.
Виклик setter прямо під час кожного рендера може спричинити нескінченні рендери.
У React назви подій пишуться camelCase: onClick, onChange, onSubmit.
e.target — елемент, де виникла подія; e.currentTarget — елемент поточного обробника.
Наприклад, клік може потрапити на іконку всередині кнопки, але currentTarget
обробника кнопки все одно означатиме цю кнопку.
Приклад у коді: src/components/ProductCard/ProductCard.tsx.


35. WHAT IS THE DIFFERENCE BETWEEN preventDefault AND stopPropagation?
Чим відрізняються preventDefault і stopPropagation?

Answer in English:
preventDefault cancels the browser's default action for an event.
In a form, it prevents normal submission and page navigation so my handler can send the request.
stopPropagation stops the event from continuing to other handlers along its propagation path.
These methods solve different problems.
One does not automatically perform the other's job.

Повний переклад українською:
preventDefault скасовує стандартну дію браузера для події.
У формі він запобігає звичайному надсиланню й переходу сторінки,
щоб мій обробник міг надіслати запит.
stopPropagation зупиняє подальше поширення події до інших обробників на її шляху.
Ці методи вирішують різні завдання.
Один не виконує автоматично роботу іншого.

Що реалізовано і для чого:
Checkout.handleSubmit викликає e.preventDefault(), після чого виконує
перевірки й submitOrder. Форма пошуку в Header робить так само перед navigate.
У useModalFocus для Escape використано обидва методи: закривається діалог,
а подія не повинна додатково запускати зовнішній обробник закриття.
Спливання події означає, що батьківський обробник може також отримати подію дитини.
Можливе уточнення: «Does preventDefault disable validation?» — ні,
це не вимикання перевірок required, email або нашої серверної валідації.
Обробник onSubmit має тип React.FormEvent; поля введення мають події зміни.
Приклад у коді: src/pages/Checkout/Checkout.tsx; src/components/Header/Header.tsx;
src/hooks/useModalFocus.ts.


36. HOW CAN A CHILD COMPONENT ASK ITS PARENT TO CHANGE STATE?
Як дочірній компонент може попросити батьківський змінити стан?

Answer in English:
The parent owns the state and passes a callback through props.
The child calls that callback when an event happens.
In Meloria, App owns isCartOpen and passes onCartOpen to Header.
Header calls it after a click, and App updates its state.
The child does not directly change the parent's state or rewrite its props.

Повний переклад українською:
Батьківський компонент володіє станом і передає callback через props.
Дочірній компонент викликає цей callback, коли відбувається подія.
У Meloria App володіє isCartOpen і передає onCartOpen до Header.
Header викликає його після кліку, а App оновлює свій стан.
Дочірній компонент не змінює стан батьківського напряму й не переписує свої props.

Що реалізовано і для чого:
App передає <Header onCartOpen={() => setIsCartOpen(true)} />.
Header приймає onCartOpen у props і викликає його через handleCartOpen.
CartDrawer отримує isOpen та onClose від App. Так обидва компоненти
узгоджено працюють зі станом відкриття кошика, який належить App.
Для самих товарів кошика використовується Context — це окрема відповідальність.
Можливе уточнення: «What is lifting state up?» — перенесення спільного стану
до найближчого батьківського компонента, щоб потрібні діти мали одне джерело даних.
Приклад у коді: src/App.tsx; src/components/Header/Header.tsx.

37. WHEN DOES useMemo RECALCULATE, AND WHAT BELONGS IN ITS DEPENDENCY ARRAY?
Коли useMemo перераховує значення й що має бути в масиві залежностей?

Answer in English:
useMemo calculates a value and can reuse it while its dependencies stay the same.
In Home, the delivery-filtered list depends on products and the selected delivery group.
When either changes, React recalculates the list.
Every changing value used by that calculation must be represented in its dependencies.
Memoization is an optimization, not a guarantee that the calculation runs only once.

Повний переклад українською:
useMemo обчислює значення й може повторно використовувати його,
поки залежності залишаються тими самими.
У Home список із фільтром доставки залежить від products і вибраної групи доставки.
Коли щось із них змінюється, React перераховує список.
Кожне змінне значення, використане в цьому обчисленні, має бути враховане в залежностях.
Мемоізація — це оптимізація, а не гарантія, що обчислення виконається лише один раз.

Що реалізовано і для чого:
У deliveryFilteredProducts залежності — [activeDeliveryGroup, products].
Оновлення кошика не змінює ці дві залежності, тому результат фільтрації може
використовуватися повторно. React порівнює залежності через Object.is.
Якщо забути products, можна отримати застарілий список після завантаження каталогу.
Якщо щоразу створювати новий об'єкт-залежність, порівняння бачитиме нове посилання,
і очікувана користь кешування зникне. Не потрібно додавати useMemo до кожного
простого обчислення: додаткова складність теж має свою ціну.
Приклад у коді: src/pages/Home.tsx, deliveryFilteredProducts і categoryCards.


38. WHEN WOULD YOU CHOOSE useEffect INSTEAD OF useMemo?
Коли варто обрати useEffect замість useMemo?

Answer in English:
useMemo is for a pure calculation whose result I need during rendering.
useEffect is for synchronization with an external system after React commits an update.
Filtering products is a calculation, so it can use useMemo.
Fetching the catalogue or saving the cart to browser storage is a side effect.
I do not use useMemo to send requests or update state.

Повний переклад українською:
useMemo призначений для чистого обчислення, результат якого потрібен під час рендера.
useEffect призначений для синхронізації із зовнішньою системою після того,
як React застосує оновлення.
Фільтрація товарів — це обчислення, тому вона може використовувати useMemo.
Завантаження каталогу або збереження кошика у сховищі браузера — це побічний ефект.
Я не використовую useMemo для надсилання запитів або оновлення стану.

Що реалізовано і для чого:
У Home useEffect виконує fetch, а useMemo виводить потрібні списки з products.
Не потрібно зберігати кожен обчислений список у додатковому state та ще одним
ефектом синхронізувати його з products: це створює зайвий стан і ризик неузгодженості.
Чисте обчислення не змінює зовнішні дані й не виконує мережевих дій.
Наприклад, filter повертає новий масив; перед sort у проєкті створюється копія,
щоб не змінювати вихідний масив товарів під час обчислення.
Можливе уточнення: «Does useEffect always run after the browser paints?» —
не варто обіцяти саме такий момент; для пояснення достатньо зв'язку з commit і залежностями.
Приклад у коді: src/pages/Home.tsx; src/context/CartContext.tsx.


39. WHAT DOES useCallback DO? DOES IT STOP A COMPONENT FROM RENDERING?
Що робить useCallback? Чи зупиняє він рендер компонента?

Answer in English:
useCallback can keep the same function reference while its dependencies stay the same.
In ProductCard, closeDetails is passed to the dialog focus hook.
A stable callback helps avoid restarting that effect only because the function reference changed.
useCallback does not call the function or stop component renders by itself.
Its dependencies still need to be correct.

Повний переклад українською:
useCallback може зберігати те саме посилання на функцію, поки її залежності не змінюються.
У ProductCard closeDetails передається до хука керування фокусом діалогу.
Стабільний callback допомагає не перезапускати цей ефект лише через зміну посилання на функцію.
useCallback не викликає функцію й сам по собі не зупиняє рендери компонента.
Його залежності все одно мають бути правильними.

Що реалізовано і для чого:
const closeDetails = useCallback(() => setIsDetailOpen(false), []);
Ефект у useModalFocus залежить від isOpen та onClose. Стабільне посилання onClose
запобігає зайвому cleanup і повторному налаштуванню ефекту через зміну функції.
Порожній масив доречний тут, бо callback використовує стабільний setter,
а не змінне значення isDetailOpen. В інших функціях потрібні інші залежності.
Якщо callback читає змінний state без правильної залежності, він може бачити
застаріле значення. useCallback не є автоматичним способом зробити все швидшим.
Приклад у коді: src/components/ProductCard/ProductCard.tsx; src/hooks/useModalFocus.ts.


40. HOW DO map, filter, find AND reduce HELP IN YOUR SHOP?
Як map, filter, find і reduce використовуються у твоєму магазині?

Answer in English:
map transforms each item, for example into a product card or an updated cart item.
filter selects matching products or selected cart items.
find returns the first matching item, such as an existing product in the cart.
reduce combines values, for example to calculate a total.
These methods help me describe data changes without directly changing the original array.

Повний переклад українською:
map перетворює кожен елемент, наприклад на картку товару або оновлений елемент кошика.
filter вибирає відповідні товари або позначені елементи кошика.
find повертає перший відповідний елемент, наприклад наявний товар у кошику.
reduce об'єднує значення, наприклад для обчислення загальної суми.
Ці методи допомагають описувати зміни даних без прямої зміни початкового масиву.

Що реалізовано і для чого:
visibleProducts.map(...) створює елементи ProductCard з key={product.id}.
cartItems.filter(item => item.selected) залишає лише позначені товари.
prevItems.find(...) визначає, чи товар уже є в кошику.
reduce((sum, item) => sum + item.product.price * item.quantity, 0) обчислює суму.
Початковий 0 задає акумулятор і дозволяє коректно обробити порожній кошик.
find може повернути undefined, якщо збігу немає; filter у такій ситуації поверне [].
map і filter створюють нові масиви, але не роблять автоматично глибоких копій об'єктів:
для зміни вкладеного елемента кошика застосовуємо {...item, quantity: ...}.
Приклад у коді: src/pages/Home.tsx; src/context/CartContext.tsx; src/pages/Checkout/Checkout.tsx.


41. HOW DOES CONDITIONAL RENDERING WORK IN YOUR PROJECT?
Як працює умовне відображення у твоєму проєкті?

Answer in English:
Conditional rendering chooses what React should display for the current state.
The catalogue shows loading, an error, an empty message or product results.
The load-more button appears only when the list has more than twenty-four products.
Its label and disabled state change when all products are shown.
These conditions connect the interface to the actual data and user actions.

Повний переклад українською:
Умовне відображення визначає, що React має показати для поточного стану.
Каталог показує завантаження, помилку, повідомлення про порожній список або результати.
Кнопка наступних товарів з'являється лише тоді, коли список містить понад двадцять чотири товари.
Її підпис і неактивний стан змінюються, коли показано всі товари.
Ці умови пов'язують інтерфейс із реальними даними та діями користувача.

Що реалізовано і для чого:
У Home використовуються тернарні умови та &&, наприклад:
{products.length > PRODUCTS_PER_BATCH && (...)}.
hasMore ? 'Показати ще' : 'Усі товари показано' обирає текст кнопки.
У Checkout formErrors.name && (...) показує пояснення конкретної помилки.
Для числової довжини краще явне порівняння length > 0, щоб вираз 0 && (...)
не вивів на сторінку число 0. true, false, null та undefined не показуються як текст.
Умовно прихована кнопка не захищає API: права й дані перевіряє сервер.
Приклад у коді: src/pages/Home.tsx; src/pages/Checkout/Checkout.tsx.


42. WHAT IS A CUSTOM HOOK, AND WHAT RULES DO HOOKS FOLLOW?
Що таке власний hook і яких правил потрібно дотримуватися для hooks?

Answer in English:
A custom hook is a function that reuses React logic and starts with use.
useCart reads the shared cart context, while useModalFocus manages dialog focus behaviour.
Hooks such as useState and useEffect must be called at the top level
of a React component or a custom hook, not inside conditions or loops.
Sharing a hook does not automatically share its local state.

Повний переклад українською:
Власний hook — це функція для повторного використання React-логіки, назва якої починається з use.
useCart читає спільний контекст кошика, а useModalFocus керує поведінкою фокуса діалогу.
Такі hooks, як useState та useEffect, потрібно викликати на верхньому рівні
React-компонента або власного hook, а не всередині умов чи циклів.
Повторне використання hook не означає автоматичного спільного локального стану.

Що реалізовано і для чого:
useCart об'єднує useContext із перевіркою, що компонент знаходиться всередині CartProvider.
Якщо провайдера немає, він дає зрозумілу помилку. Саме Provider робить кошик спільним.
useModalFocus повторно використовує логіку фокуса для різних діалогів,
але кожний виклик має власний ref. Хук можна викликати завжди, а перевірку
if (!isOpen) робити всередині його ефекту, не порушуючи порядок викликів hooks.
React покладається на послідовність цих викликів між рендерами.
map може створювати багато <ProductCard />, кожен зі своїми hooks;
це відрізняється від прямого виклику useState всередині циклу батьківського компонента.
Приклад у коді: src/context/cartContextValue.ts; src/hooks/useModalFocus.ts;
src/components/ProductCard/ProductCard.tsx.
